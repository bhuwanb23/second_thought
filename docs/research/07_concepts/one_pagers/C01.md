# C01 — The Integration Doctor

*One-pager · EV #1 (68.3) · intent fit 5/5 · 2 competitors · STRONG, but derivative-risk-bound*

---

## 1. The sentence

**"Your PayPal integration is running on a deprecated SDK. Point this agent at your repo and it upgrades, validates and certifies it — in minutes, with a signed report you can hand to your CTO."**

## 2. Who hurts, and how much

**Audience:** developers and technical founders at small-to-mid merchants, plus agencies maintaining several client integrations.

The pain is not speculative — it is **measurable in install counts**:

| Evidence | Number |
|---|---|
| `paypalrestsdk` (PyPI, last release **1 Nov 2023**) | **990,808 installs/month** |
| `paypal-server-sdk` (PyPI, the replacement) | **30,749 installs/month** |
| `checkout-server-sdk` (npm, legacy) | **234,050 installs/month** |
| `paypal-server-sdk` (npm) | 618,851/month |
| JS SDK v6 usage across the 549-repo field | **1%** |

→ Roughly **1.2 million legacy Python installs per month against 31 thousand modern ones.** The migration has barely started.

Plus a hard, dated deadline: **Braintree Drop-in SDK was deprecated on 1 Oct 2026 and becomes unsupported on 1 Oct 2027.** Every merchant on it has 12 months.

Ledger entries: **P01–P06**. Evidence strength: **strong** (install telemetry and repo metadata, not survey).

## 3. What the user does

1. Paste a GitHub repo URL (or upload a zip).
2. The agent indexes the code and **locates the PayPal integration** — which SDK, which version, which endpoints, which flows.
3. It produces a **findings list**: deprecated SDK, missing webhook signature verification, `intent: AUTHORIZE` followed by `/capture`, hardcoded credentials, no idempotency key, CAPTURE-only where a hold is needed.
4. It **generates a patch** — SDK swap plus the specific code changes — and applies it on a branch.
5. It **runs the sandbox test suite it generated**, executes a live Orders v2 AUTHORIZE → CAPTURE against PayPal sandbox, verifies the webhook signature round-trip.
6. It emits a **certification report**: pass/fail per rule, a score, the diff, and a signed PDF/JSON artefact.

## 4. What the agent decides vs. what code decides

| Agent | Deterministic code |
|---|---|
| Reads the codebase, identifies the integration surface and its intent | Every rule check is a static-analysis or live-API assertion with a pass/fail result |
| Drafts the patch and explains the rationale | The sandbox test suite is generated from the rule set, not from the model's opinion |
| Summarises findings in plain English | Certification verdict comes from test exit codes, never from the model |

**The model may not certify anything.** It proposes; the test harness decides. State this on screen — it is the same boundary every top entry in the field drew.

## 5. PayPal surface

| API / tool | Why it is the right primitive |
|---|---|
| **Orders v2** (`/v2/checkout/orders`) | The target of the migration; the report verifies the merchant's flow against it |
| **AUTHORIZE → CAPTURE** | Only 9% of the field uses it; the doctor checks intent/endpoint consistency |
| **Webhooks + `/verify-webhook-signature`** | The single most common security gap in real integrations |
| **Agent Toolkit / MCP** | The doctor itself is an agent over a merchant's codebase |
| Sandbox REST | Every validation is executed, not asserted |

## 6. Why now

**10 Aug 2026 — Ai4.** CTO Srini Venkatesan demoed a Merchant AI Integration Agent that "reads a merchant's codebase, understands its PayPal integration, and automatically upgrades, validates, and certifies compliance with the latest version… certification now takes **hours rather than weeks**."

That is the same product. Which is the problem and the opportunity in one.

## 7. Why this is not already covered

`merchant-integration` is the **second-thinnest cluster in the field: 2 repos out of 549.**

But read the caveat honestly: one of those two is `Thinkelution/paypal-retrofit` (depth 10), which *"lets an AI agent wire PayPal into a business system that already exists."* That is **connecting PayPal where it is absent**. C01 is **upgrading and certifying PayPal where it is already present but stale**. Different user, different task, different artefact. The overlap is flavour, not function — but in a 2-repo cluster, that distinction has to be visible in the first fifteen seconds of the video.

## 10. What makes this derivative — and the escape routes

**The risk, stated plainly:** on 10 Aug 2026 PayPal's CTO publicly demoed an agent that does exactly this. Every judge from PayPal developer relations has likely seen it. "You built our announced product, smaller" is a real possible reaction.

**Three escape routes, in order of strength:**

1. **Go where their product cannot go — the long tail and open source.** Their agent "runs on the merchant's own computing infrastructure" and targets merchants with a codebase and a developer. Extend to **no-code storefronts** (WooCommerce, Shopify, Squarespace), to **non-US merchants**, and to **agency-scale multi-client certification** where one tool certifies fifty integrations. That is the same gap Store Sync leaves (US-only, invitation-gated).
2. **Extend from "correct" to "agentic-ready."** The certification should also check: does this integration support agent-initiated payment? Verified webhooks, idempotency, AUTHORIZE for holds, order state machine correctness, mandate references. Call it **Agent-Readiness Certification** — that maps directly onto the "Best Use of Agentic Commerce" prize and is a category PayPal has not shipped.
3. **Ship the portable artefact.** A signed, versioned, machine-readable certification (`paypal-cert.json`) that a merchant can put in their repo README and an agency can hand to a client. Products announce; artefacts spread.

**Do this if** you can commit to framing #2 (agentic readiness) from the opening sentence. **Do not do this** as "we reimplemented your August demo."

**Conditional on:** finding a genuinely stale real-world integration to demo against. If the demo repo has to be fabricated, the credibility collapses.
